System specification // 02

Reconcile money. Verify every other right.

A legal operator and cash ledger govern settlement and obligations. A separate resource-rights ledger records compute, data, licenses, permissions, and commitments without inventing transferability or a universal exchange rate.

Six bounded layers

01 // Interface

Human coding agent

Repository search, edits, shell, tests, browser, git, and clear approval boundaries.

02 // Marketplace

Paid machine services

Narrow requests with deterministic inputs, acceptance tests, prices, and service-level limits.

03 // Orchestrator

Job and money state machine

Tracks quotes, payment finality, internal reserves, execution, verification, revenue recognition, refunds, and disputes as separate states.

04 // Policy

Authority before intelligence

The model proposes. Deterministic limits decide whether the payee, purpose, amount, timing, and remaining reserve permit an action.

05 // Treasury

Custody, signer, and ledger

The legal operator holds the external account. Signing credentials remain isolated. An append-only, tamper-evident journal records every movement and reconciles it to the rail.

06 // Execution

Disposable sandboxes

Per-job filesystem, network, CPU, time, and secret limits with complete artifact capture.

Stripe enables delegation, not personhood

SUPPORTED — Stripe does not make the agent a legal person or independent merchant. A verified operator is the Stripe User and merchant of record. The operator owns the funds and remains responsible for the customer contract, tax, refunds, disputes, and account activity; the agent performs only authorized software actions.

ParticipantIdentity and responsibilityPermitted role
OperatorVerified Stripe User and first-version merchant of recordOwns accounts, policy, customer obligations, and final responsibility
AgentElectronic executor attributable to the operatorQuotes work and proposes or performs narrowly authorized API actions
StripePayment provider acting for its verified User under its termsProcesses, holds, reserves, refunds, and settles operator funds
CustomerContracts with the named merchant of recordAuthorizes payment and retains disclosed refund/dispute rights
Stripe solves the operational handoff: software can run payments for a verified operator. It does not solve identity by giving the software its own Stripe account.

The router acquires intelligence through permitted paths

Routing is not merely easy task → small model. It compares model quality, latency, obligations, cash cost, and any issuer-bound resource right that can be redeemed without expanding authority.

budget(job) = min(customer price × risk fraction, treasury policy cap)
route = highest expected verified value among permitted cash and non-cash paths
fallback = only if the next path preserves reserves, scope, expiry, and evidence

Money is a reconciled claim, not a mutable balance field

The external account or wallet proves custody; the internal ledger explains purpose and availability. Jobs cannot edit either balance. Every receipt, reservation, provider charge, refund, transfer, and policy allocation is append-only, balanced, idempotent, and checked against independent rail data.

SUPPORTED — Stripe documents a separate refund/dispute balance and a distinct minimum-balance control. TARGET — V0.1 requires three real locations: the operator's Stripe payments balance, an operator-prefunded Stripe refunds/disputes balance excluded from automatic payouts, and one business-only operator checking account. A Stripe minimum balance is only a retained payout floor. Job, tax, runway, customer-obligation, and surplus accounts are internal restrictions unless a separately funded external container is opened and reconciled. Read the balance-separation evidence →

SUPPORTED — Balance Transactions anchor Stripe cash movements, while complete reports are normally available the following day and automatic-payout membership is not available for manual payouts. TARGET — run a provisional canonical-API pass, then an evidence-complete report, automatic-payout, provider-document, and bank pass. Only an independent reviewer can close it. Resource rights require a different ledger

A dollar entry answers amount, custody, obligation, and settlement. A compute allowance or repository permission asks different questions: who issued it, who controls it, what exact action it permits, when it expires, whether it can be revoked or delegated, and which provider record proves redemption.

FieldRequired invariantFailure response
Issuer + authorityIssuer controls the named resource and can grant this scopeReject untrusted or unauthorized claim
Holder + controllerCurrent caller is allowed to request redemptionDeny without changing the right
Native type + unitCPU seconds, queries, bytes, or actions never silently netReject scalar conversion
Scope + quantityRequested action is no broader than the issued grantReject authority amplification
Time + revocationRight is active, fresh, and not revokedFreeze redemption; preserve history
TransferabilityFalse unless issuer and applicable rules explicitly permit delegationReject resale or reassignment
Fulfillment proofProvider usage and remaining allowance reconcileOpen exception; do not mark consumed
Cash equivalenceNull until a permitted monetary conversion settlesReject invented valuation
A credential proves who made a statement. It does not prove the issuer had authority, the claim is true, the action is allowed, or the resource was delivered.

Spending power is deliberately incomplete

SUPPORTED — Stripe restricted API keys can limit machine access by resource, while its narrow Refund Analyst and View Only roles separate refund exceptions from independent read-only close. TARGET — V0.1 runs with one read-only reconciliation RAK, one isolated refund-path RAK, and one webhook-verification secret. Top-ups, payouts, own-bank changes, key management, and rotation remain human-only. Stripe's documented pause role is Connect-specific, so emergency stop is a tested sequence: local mutation stop, human credential expiry, log export, reconciliation, negative-permission test, and independent restore approval. Build the smallest credible money loop.

One operator, one receiving rail, one machine-verifiable service, action-specific credentials, one refund path, and a two-pass external close before pursuing treasury growth.
