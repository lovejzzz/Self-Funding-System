Abstract

Standing conclusion · version 2026-08-25

SELF/FUNDING is not yet an observed self-financing or self-provisioning agent. It is a bounded research program asking whether verified software contribution can replenish future action capacity through two distinct systems: accountable money for settlement and obligations, and issuer-bound resource rights for compute, data, licenses, permissions, and reciprocal commitments.

Current infrastructure supports tool-using agents, model routing, programmatic payments, scoped authorization, digital credentials, sandboxing, idempotency, and reconciliation. It does not yet prove durable demand, positive repeated contribution, independent agent identity, a live multi-resource exchange, or a surplus large enough to subsidize free human access.[1][87][92]

Direct fact

Stripe delegates operations; it does not grant personhood

Stripe still requires an identifiable User and merchant of record. A verified operator can let software create bounded payment objects and read events, but the agent does not own the account or funds. Connect moves merchant responsibility between platform and connected account; it does not remove it.[4][5][6][7]

  • ACP and Shared Payment Tokens primarily support buyer-agent authorization while the business remains seller and merchant.
  • U.S. federal law recognizes electronic-agent involvement when its action is legally attributable to the person being bound.[8]
  • Current path: operator owns obligations; agent acts under narrow, auditable permissions.

00:42:22 UTCRound 05 · money state machine
Direct fact + bounded inference

A successful card payment is not one final state

PaymentIntent success permits fulfillment, but the linked net funds can still be pending. Stripe availability permits debit and payout, but refund, dispute, and payout-failure exposure remains. The buildable conclusion is to track payment flow, external custody, customer obligation, and internal allocation as separate dimensions.[11][12][13][15]

  • Counterevidence: Stripe explicitly supports fulfillment at PaymentIntent success; waiting for bank payout is not a universal requirement. If customer funds are still pending, however, paid provider work needs separately confirmed working capital.
  • State regression: a refund may later fail, and a payout shown as paid can change to failed within up to five additional business days.[14][16]
  • Unknown: account-specific reserves, legal segregation, revenue recognition, and reserve sizing still require live evidence and US legal/accounting review.
  • Experiment: replay Stripe's dispute, asynchronous-refund, available-balance, duplicate-event, and out-of-order-event fixtures before one small live payment and real refund.[17][18][19]

00:59:44 UTCRound 06 · collection + API fuel
Direct fact + buildable decision

Economic self-funding is possible before independent agent ownership

Mainstream providers do not currently expose a documented, general credit-purchase API for an agent. They do support operator-configured auto-recharge or pay-as-you-go, so an agent can economically finance later inference without owning the billing account.[20][21][22][23]

  • OpenRouter: it supports auto top-up and a read-only Credits API, but the old programmatic Coinbase purchase endpoint now returns 410 and directs users to a web purchase flow.[24][25][26][27]
  • Best fiat path: Stripe Projects can provision scoped OpenRouter pay-as-you-go access with global/provider caps. Square offers another short operator-owned route from seller receipts to an eligible US checking/debit account.[28][29][30][31]
  • Other collection: a MoR can absorb customer-facing tax/refund work but pays the operator later; bank invoices suit larger B2B work, not an instant microservice loop.[32][33]
  • Most agent-native path: an x402 endpoint can earn USDC to a wallet that later pays another x402 endpoint. Coinbase's MCP deliberately keeps onramp, arbitrary transfers, and limit changes human-controlled.[34][35][36]
  • Unknown: live provider acceptance, charge timing, account reserves, model coverage in x402, tax treatment, and exact gateway resale terms remain unresolved.

01:44:21 UTCRound 07 · provider reconciliation
Direct fact + exact blocker

Stripe Projects delegates payment; it does not yet prove the provider cash trail

A paid Projects upgrade turns the operator's stored payment credential into a Shared Payment Token. OpenRouter, as provider, uses that token to create the provider-side PaymentIntent. The SPT is authority to charge—not funds, a sales-balance transfer, or a job ledger.[37][38][29]

  • Supported control: Projects offers global/provider caps and provider-month spend; OpenRouter offers per-generation usage plus key/model guardrails.[37][39][40]
  • Counterevidence: SPT issued-token events and ordinary seller PaymentIntent reporting may supply a payment anchor, so the path is not inherently unreconcilable.[38]
  • Unknown/conflicting: public docs do not state whether Projects charges per generation, replenishes OpenRouter credits, aggregates usage, or exposes SPT, PaymentIntent, receipt, retry, 3DS, and refund linkage to the operator. OpenRouter's general path still describes credits and delayed credit appearance after Stripe purchase.[24]
  • Decision: use Projects for provisioning, scoped credentials, and an outer cap, but label the paid loop RECONCILIATION_BLOCKED. Projects spend is an aggregate cross-check, not proof of job-level settled provider cost.

02:12:52 UTCRound 08 · balance separation
Direct fact + buildable decision

Protect refund liquidity physically; label the other buckets honestly

Stripe exposes a separate, operator-funded future-refund/dispute balance that automatic payouts do not drain. Its minimum-balance setting is only a retained payments-balance floor; it can be changed and can still be exceeded. V0.1 therefore needs three real locations—Stripe payments, Stripe refund prefunding, and business-only checking—while job, tax, runway, obligation, and surplus remain internal restrictions unless separately funded.[41][42][43][44]

  • Accounting boundary: ASC 606 presents pre-delivery customer consideration as a contract liability; that classification does not itself create a trust or separate cash account.[45]
  • Counterevidence: Stripe is not one undifferentiated balance, but its refund prefunding is second in the debit order after available payments funds and both sources can be exhausted.[42]
  • Negative result: the reviewed primary sources did not prescribe separate US bank accounts for a generic merchant's tax, job, and general reserve. IRS guidance does call for business-only checking, books, and reconciliation.[46]
  • Unknown: actual account feature access, buffer sizing, entity/state/tax treatment, and any activity-specific segregation duty require account evidence and US professional review.

02:44:43 UTCRound 09 · credential authority
Direct fact + buildable decision

Runtime gets two narrow keys; treasury changes stay human

Stripe supports resource-scoped restricted API keys and explicitly recommends them for AI agents. V0.1 can therefore split normal operation across one read-only reconciliation RAK, one isolated refund-path RAK, and an endpoint-specific webhook-verification secret—without giving the runtime an unrestricted key or Dashboard session.[47][48]

  • Human boundary: Refund Analyst can refund without balance, payout, bank, or key access; View Only can review payments, balances, payouts, logs, reports, and security history without mutation. Top-up, payout settings, own-bank changes, and key rotation remain human-only.[49][50]
  • Counterevidence: Analyst combines refund and payout, Developer reaches an almost-all-API secret key, and Administrator combines refund, payout, key, bank, and schedule changes. Multiple roles add permissions, so these are not runtime identities.[49]
  • Negative result: Stripe's documented pause role is Connect-specific. The reviewed sources did not establish a standard-account one-click stop or native two-person approval; emergency stop must compose local mutation denial, human key expiry, log export, reconciliation, and tested restore.
  • Pre-live gate: prove positive and negative RAK calls, refund idempotency, webhook signature and secret-roll behavior, old-key expiry, role boundaries, security-history capture, local stop, and a zero-difference sandbox close.[47][48][51][18]
  • Unknown: live feature access, exact account permission labels, real prefunding/bank verification, payout limits, and enterprise approval controls still require account evidence. This is a US operator product-control design, not legal, accounting, tax, security, or financial advice.[52][53]

2026-08-24
02:52:25 UTCRound 10 · identity gap map
Direct fact + bounded inference

Machine identity exists; recognized economic identity does not

DID, verifiable credentials and agent-signed mandates already support persistent machine identity and bounded authorization. The break occurs when those proofs meet legal attribution, beneficial-owner/control-person checks, named account ownership, provider billing and recovery. A keypair can identify an agent; it cannot make a bank or API provider treat that agent as an independent customer.[54][55][56][57]

  • Legal boundary: US electronic-agent law validates transactions when the action is attributable to the person bound; Stripe and OpenAI continue to assign account, payment and activity responsibility to an identifiable User or Customer.[58][4][22]
  • Financial boundary: a verified entity can give an agent dedicated accounts, subledgers, scoped keys and a virtual card, but FinCEN still requires natural-person ownership/control information and current agent wallets reserve onramp, arbitrary transfer and limit changes to the user.[57][35]
  • Provider boundary: OpenAI now exposes service-account, usage/cost and spend-control operations plus Billing-UI auto-recharge, but its public reference still does not expose a general mandate-bound credit-purchase operation.[20][21]
  • Buildable target: persistent agent identity + operator legal wrapper + root mandate + credential lineage + revocation + recovery quorum + action-specific signer + independent close. A card is only a compatibility adapter.
  • Largest internal gap: prove one real payment → delivery/refund → full-cost close → API fuel → next accepted output loop before claiming observed self-funding.

03:11:02 UTCRound 16 · beyond money
Standing correction + measured bridge

Money is one resource rail, not the definition of agent wealth

The frontier model now defines operational wealth as a typed portfolio of rights that changes which permitted futures the system can reach. Cash remains essential for settlement and obligations; compute, data, licenses, permissions, reputation, and reciprocal commitments remain issuer-bound, non-fungible records.[87][88][92][98]

  • Direct facts: algorithmic cycles and memory can overcome some double-coincidence constraints without money; cloud credits fund future service while official terms deny cash value and restrict transfer; repository roles change the holder's available actions.[89][90][94][95][96]
  • Boundary: credentials can authenticate issuer claims but do not prove truth, authority, acceptance, or fulfillment. Reputation is contextual evidence, not transferable inventory.[92][93][97]
  • Measured locally: one three-party fixture matched 3,600 CPU seconds, 100 data queries, and one repository-triage action. Three simulated rights were consumed once; seven transfer, cash-equivalence, quantity, scope, duplication, and connectivity corruptions were rejected.
  • Counterevidence: no external right was issued or honored, no live atomic exchange occurred, and no reviewed source establishes a general-purpose multi-resource agent economy.
  • Buildable decision: retain the reconciled money ledger and add a separate resource-rights ledger with native units, issuer authority, holder, scope, expiry, revocation, transferability, redemption evidence, and a default cash_equivalent=null.
  • Evidence ceiling: SIMULATED_RESOURCE_EXCHANGE → LOCAL_CONTROL_PLANE_ONLY.
